# Developer onboarding: Blazor, APIs, and the decision engine

Repository orientation reviewed against source on 2026-10-07.

**Audience:** a developer comfortable with C# and ASP.NET Core who knows Aspire but has never used Blazor. **Target:** 1–2 working days, then small reviewed contributions by the end of the week. Prefer the two-day route: Blazor needs hands-on practice, and authentication decisions deserve careful review.

By the end, you should be able to run the advisor, explain an answer's path from a Razor component to a validated plan, make a small UI change, extend guide/API templates, and write a focused engine regression test. This is preparation for contributing with review, not independent ownership of every OAuth or tenant configuration.

## 1. Understand what you are developing

The product helps a developer describe an architecture, choose Entra authentication approaches, and follow/export implementation instructions. It is **standalone Blazor WebAssembly**, using MudBlazor. The advisor's UI, engine, and guide generator execute in the browser. It has no application backend, database, or advisor sign-in. Answers and completion state are temporary and reset on reload.

There are two different applications to keep in mind:

| Application | Execution and responsibility |
| --- | --- |
| The advisor you are editing | Browser C# UI, deterministic evaluation, guide generation, static deployment |
| Applications described/generated by the advisor | Can include a server-interactive Blazor Web App, ASP.NET Core APIs, workers, and other clients; their authentication requirements depend on the selected architecture |

The repository's API work currently means **generated API configuration/code, validation exports, and modeled API responsibilities**. There is no existing advisor API endpoint to extend. A new advisor backend would be an architectural feature requiring separate design. Aspire AppHost and ServiceDefaults are retained optional local tooling, outside the deployed browser client; your Aspire knowledge is useful context but is not the starting path.

Some documents preserve earlier milestone evidence. Current hosting and feature ownership are described in [hybrid architecture](hybrid-architecture.md). The advisor uses browser-session state; its generated Blazor server sample has a different execution model. Resolve historical implementation statements against current source.

## 4. Learn only the Blazor you need first — day 1

Blazor renders UI from C# components. A `.razor` file combines HTML/component markup with C#; it is a component instance with state and lifecycle, rather than an MVC view executed once per request. When an event changes state, Blazor normally renders the affected component again. Keep markup expressions and render-time getters free of side effects.

Read these official references selectively, then locate each concept in this repository:

| Concept | What to learn | Repository example |
| --- | --- | --- |
| [Razor components](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/?view=aspnetcore-10.0) | `@code`, `@if`, `@foreach`, typed parameters, component composition | `Features/DesignArchitecture/ChoiceCards.razor` |
| [Events](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/event-handling?view=aspnetcore-10.0) | `@onclick`, method handlers, `EventCallback<T>`, returning `Task` | `Home.razor`, `ChoiceCards.razor` |
| [Binding](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/data-binding?view=aspnetcore-10.0) | `@bind`, and explicit value/change callback pairs | `Selected`/`SelectedChanged` in `ChoiceCards` |
| [Lifecycle](https://learn.microsoft.com/en-us/aspnet/core/blazor/components/lifecycle?view=aspnetcore-10.0) | Initialization, changed parameters, post-render DOM access | `DesignJourneyState`, `Home.OnAfterRenderAsync`, `ImplementationJourney.OnAfterRenderAsync` |
| [MudBlazor usage](https://mudblazor.com/getting-started/usage) | Library components, services, providers; inspect pinned-version usage in this repo | `Program.cs`, `MainLayout.razor` |

Spend roughly 15 minutes on each reference, then practice. The repo pins MudBlazor 9.11.0 and WebAssembly 10.0.11; current documentation examples may differ from these package versions.

### Translate your ASP.NET Core knowledge

- `@page "/"` makes a component routable. `Routes.razor` and `MainLayout.razor` handle routing/layout; `_Imports.razor` supplies shared Razor imports.
- `@inject AdvisorWorkspace W` uses DI, but this DI container is in the browser. Its scoped workspace lives in the running browser app, rather than in an ASP.NET request or server circuit.
- `[Parameter]` supplies input from a parent. Treat input as parent-owned; notify the parent through a callback when it should change. `[EditorRequired]` helps tooling identify missing input; it does not replace runtime validation.
- `EventCallback<string>` communicates a selected value upward. In this app, selection initially changes `DesignJourneyState`'s draft dictionary; Continue applies the answer to the engine. Selecting and committing are distinct actions.
- `@bind` combines a value and change handler. Do not also specify the same generated change handler. MudBlazor uses typed component callbacks such as `OnClick` and `ValueChanged`, not always native HTML event attributes.
- Use `async Task` for asynchronous handlers, await work, and avoid `async void`. Blazor normally schedules rendering after events; do not scatter `StateHasChanged()` calls to mask an ownership problem. External notifications may require `InvokeAsync` and explicit rendering.
- `OnInitialized` handles one-time initialization. Use `OnParametersSet` when derived state must track new parent inputs. `OnAfterRenderAsync` is where rendered element references become usable. Guard post-render state changes against endless render loops.
- `@key` preserves/replaces component identity as items or plans change. Inspect question and plan keys in `DesignArchitecture` and `ImplementationJourney`; removing them can retain stale child state.
- `IJSRuntime` bridges to browser JavaScript for actions such as downloads and focus. Inspect `wwwroot/advisor.js`; browser APIs are not ordinary .NET file writes.
- Razor renders text with escaping. Be cautious with raw HTML/`MarkupString`. Browser code and downloaded configuration are visible to the user; server secrets cannot be protected there.

### Temporary component drill (30–45 minutes)

On your own working branch, add a temporary `Components/Shared/OnboardingCounter.razor`:

```razor
<button type="button" @onclick="Increment">Practice count: @Count</button>

@code {
    [Parameter] public int Count { get; set; }
    [Parameter] public EventCallback<int> CountChanged { get; set; }

    private Task Increment() => CountChanged.InvokeAsync(Count + 1);
}
```

Render it temporarily in `Home.razor` using `<OnboardingCounter @bind-Count="practiceCount" />` and add `private int practiceCount;` inside Home's existing `@code` block. If your editor cannot resolve the component, inspect `_Imports.razor` and add the appropriate namespace import.

Click three times. Explain why the child asks the parent to update the count rather than assigning its parameter. Replace `@bind-Count` with `Count="practiceCount" CountChanged="value => practiceCount = value"` and confirm identical behavior. Add a temporary `OnAfterRenderAsync` breakpoint/log and observe when it runs. Remove the drill and parent additions before preparing a contribution.

Trace this path with your editor; use breakpoints if browser debugging is configured, or inspect corresponding tests:

```text
ChoiceCards.SelectedChanged -> DesignJourneyState drafts -> DesignArchitecture.Continue
  -> AdvisorWorkspace.Apply -> QuestionnaireSession.Apply
  -> dependency invalidation + ArchitectureEvaluator.Evaluate
  -> replacement session/evaluation
  -> Home.Generate -> GenerateGuide.Execute -> ArchitectureGuideGenerator.Generate
  -> AdvisorWorkspace.SetGuide -> typed guide components / exporters
```

Inspect `GuideIsCurrent`: it compares the guide's plan ID with the current evaluation plan. Inspect `GuideCompletionInvalidator` and `WorkspaceTests`: a changed answer must invalidate affected/dependent completion; an unchanged answer should preserve it. A plan from an earlier architecture is never an acceptable fallback when the new result needs clarification.

**UI exercise:** add a concise, conditional completion summary to the implementation UI, or improve one fact-specific help explanation in `ChoiceCards`. Keep decision logic out of the component. For a summary, derive counts from `W.Completion` rather than introducing a second completion collection. For help text, preserve question IDs, labels, and `aria-describedby` connections.

Verify a fresh journey, Back/Continue, a changed answer, regeneration, completion, reset, export, keyboard navigation, and a narrow browser width. Watch the Console for errors and check that focus still reaches the question/step heading. Compare Markdown if you changed shared guide content. A UI-only string change does not require a new artificial unit test; browser verification matters because existing tests do not prove rendered accessibility or layout.

## 6. Understand and safely change the rules engine — day 2

Read [engine behavior](engine-behavior.md), [questionnaire model](questionnaire-model.md), then the implementation. This engine is explicit C# logic, not a runtime plugin/interpreter. Editing catalog metadata alone does not implement a decision.

Key contracts and invariants:

1. `Fact<T>` distinguishes Unknown, Known, and NotApplicable, and supplied versus derived origins. Check state or `TryGetValue` before `Value`; default `false`/enum zero is not an answer. Reevaluation removes stale derived decisions.
2. Shape/integrity validation establishes Invalid before unsupported boundaries. Missing required facts return NeedsClarification. Only Ready contains a usable coherent plan. Follow the actual `Evaluate` call order and assembly helpers.
3. Sign-in belongs to components; token acquisition and authorization belong to relationships. APIs also validate incoming tokens even with no downstream calls.
4. Browser clients cannot protect confidential credentials. Delegated calls and application calls are explicit choices; user initiation does not make a downstream app-only call OBO.
5. OBO requires an applicable incoming user-token relationship and a distinct downstream audience. The modeled external-user marker is not a token. Current certificate/OBO and topology limits are intentional boundaries.
6. Equivalent normalized input and rule version must produce identical plans/traces. Keep clocks, randomness, network calls, and UI dependencies out of evaluation. Stable ordering does not resolve incompatible security decisions.
7. Exact permissions and deployment identifiers are placeholders, not guessed broad access. Ready does not verify consent, policy, tenant state, or resource compatibility.

**Engine exercise (no production behavior change required):** open `ArchitectureEvaluatorTests`, `EngineInvariantTests`, `QuestionnaireTests`, and `ScenarioExamples`. Choose an existing scenario and write a focused additional test for a meaningful adjacent boundary, such as an unknown downstream identity producing clarification without a plan, or an application incoming identity being rejected for a delegated OBO relationship. Check existing tests first to avoid duplicating them. Use `with` expressions to alter only the fact under examination; assert status, the relevant issue/question identifier, and absence of a plan where appropriate. Explain what incorrect behavior the test would catch.

For an actual new rule/architectural fact, map changes before coding:

- Contract and scenario validation/normalization, if the input shape changes.
- Evaluator behavior plus stable catalog ID, phase, rationale, and individually reviewed primary sources.
- Question definitions/options, relevance, dependency edges, scheduler, presets, and answer application as needed.
- Plan compatibility/version implications, guide generation, completion invalidation, rendering, and every affected exporter.
- Positive case, negative/unsupported case, unanswered facts, changed-answer behavior, and deterministic output tests.

Run relevant classes first, then the full suite for a decision/guide change. Discuss semantic version/schema compatibility with the reviewer; a changed label is different from a changed identity decision. Do not silently relax a security boundary to make a test pass.

## 7. Work on the ASP.NET Core API parts — day 2

Read [vertical slice](vertical-slice.md) for sample behavior, with the hosting correction in section 1 in mind. Generate the chain from the root:

```powershell
dotnet restore tools/SampleWriter/SampleWriter.csproj --locked-mode
dotnet build tools/SampleWriter/SampleWriter.csproj --no-restore -m:1 -p:UseSharedCompilation=false
dotnet tools/SampleWriter/bin/Debug/net10.0/SampleWriter.dll

dotnet restore .artifacts/generated-samples/Web/Web.csproj
dotnet restore .artifacts/generated-samples/ApiA/ApiA.csproj
dotnet restore .artifacts/generated-samples/ApiB/ApiB.csproj
dotnet build .artifacts/generated-samples/Web/Web.csproj --no-restore -m:1 -p:UseSharedCompilation=false
dotnet build .artifacts/generated-samples/ApiA/ApiA.csproj --no-restore -m:1 -p:UseSharedCompilation=false
dotnet build .artifacts/generated-samples/ApiB/ApiB.csproj --no-restore -m:1 -p:UseSharedCompilation=false
```

These files are generated into an ignored folder. **Edit `DelegatedChainTemplates.cs` and related generators, not generated output as the lasting fix.** Regenerate and rebuild to validate the exact artifacts the user receives. Not every supported architecture has the same complete runnable sample coverage; inspect generator dispatch rather than extrapolating from this chain.

Inspect the generated files in this order:

1. `Web/Program.cs`: Microsoft.Identity.Web sign-in, downstream acquisition, HTTP client and request pipeline. This sample is a server-interactive Blazor Web App, unlike the advisor.
2. The generated Web page and `Web/Controllers/CallController.cs`: the button navigates to a protected HTTP endpoint. Token acquisition occurs with request-scoped authentication, with consent/claims handling, rather than assuming a persistent component has a current request `HttpContext`.
3. `ApiA/Program.cs` and `ApiA/Controllers/DataController.cs`: incoming JWT authentication and delegated scope enforcement precede downstream OBO acquisition. Identify the downstream scope, audience, and certificate configuration.
4. `ApiB/Program.cs` and `ApiB/Controllers/DataController.cs`: validate the token for API B and enforce its required scope. API A's incoming token must not simply be forwarded to API B.
5. Configuration files: list every `__PLACEHOLDER__` and identify which registration/component owns it. Private keys and tokens do not belong in advisor state or commits.

**API/template exercise:** make a small improvement to a generated endpoint's example response or explanatory instruction, preserving authentication, scope checks, claims propagation, and configuration keys. Add an appropriate assertion to `GuideGenerationTests` or `ArchitectureGuideTests` if generated content behavior changed. Regenerate and compile all three projects. Explain why a passing string assertion alone would not prove that a generated controller compiles.

Compilation proves syntax and package compatibility; it does not prove authentication. Running a real chain requires a permitted test tenant, registrations, consent, filled configuration, and certificates. Keep this outside the onboarding critical path. For later tenant validation, use the generated instructions and [validation exports](validation-exports.md), checking a valid call, missing/invalid token, wrong audience, missing scope/role, denied consent, and claims challenges where applicable. Generally distinguish authentication failures (401) from authorization failures (403), but assert the generated application's documented behavior. Never treat a synthetic local probe as real Entra validation.

## 8. Put the layers together and prepare a contribution

Use this bounded feature drill: **improve the explanation of API token validation so users understand which audience and permissions each API checks.** First determine whether the missing explanation belongs in typed guide content, a UI-only explainer, or an export. Inspect `TokenValidationExplainer.razor`, `ArchitectureGuideGenerator`, and the guide contracts before adding anything.

Write acceptance criteria before coding:

- An API with no outgoing calls still explains incoming validation and authorization.
- A chain clearly distinguishes API A and API B audiences and scopes.
- The explanation follows delegated/application identity where relevant without changing the engine's selected flow.
- Shared instructions appear consistently in UI and Markdown; intentionally UI-only help is identified as such.
- Editing the architecture cannot display obsolete guide content or revive invalid completion.

For the two-day plan, implement a small slice if time permits. Otherwise finish the affected-file map, test choice, and concrete wording as a reviewable first-issue proposal. Avoid bundling a new OAuth flow or contract redesign into onboarding.

dotnet test tests/EntraAdvisor.Tests --no-restore --filter 'FullyQualifiedName~WorkspaceTests|FullyQualifiedName~QuestionnaireTests'

# Fast feedback for engine work:

The README estimates about eleven minutes for the exhaustive matrix. Use the filtered suite for focused hosting/UI iterations; retain the exhaustive suite for decision/guide-content changes. Run it while reviewing your diff rather than at the last minute. For sample changes, also perform the generated-project builds above. For export changes, inspect the actual downloaded artifact and relevant exporter tests. For static hosting changes, follow [static deployment](static-deployment.md) and verify the published base path/assets.

Before review, remove the temporary drill, run the solution build, inspect `git diff --check` and `git diff`, and confirm generated artifacts or secrets were not accidentally added. Update durable docs when behavior changes, following the repository's delivery guidance. A contribution description should state the user-visible change, checks performed, and any unverified tenant behavior.

### Troubleshooting shortcuts

| Symptom | First checks |
| --- | --- |
| SDK/locked restore fails | `dotnet --info`, `global.json`, feed access; do not delete lock files as a workaround |
| An edit does not appear | Start script does not rebuild; build, restart, and reload; inspect Console/static asset loading |
| Child selection does not update parent | Parameter/callback names and types; await callback; distinguish draft from committed answer |
| UI updates but plan does not | `DesignArchitecture.Continue`, relevance, `Workspace.Apply`, returned immutable session/evaluation |
| Implementation cannot open | Evaluation status/issues and required facts; never force a plan past NeedsClarification |
| Old guide/completion survives an edit | Plan ID, `GuideIsCurrent`, changed-fact dependency closure, invalidator, template compatibility |
| Dialog fails or looks wrong | Mud service registration/providers, typed parameters, browser errors and pinned component APIs |
| Download/focus fails | JS function loaded from `advisor.js`, matching invocation name, post-render element reference |
| Generated API build fails | Correct template first, regenerate, inspect generated file and pinned sample packages |
| Generated API returns 401/403 | Token's intended audience/issuer, required authorization, registration/consent; no disabling validation |

## 9. Readiness review: 30 minutes with a teammate

Demonstrate the app and explain your diff. You are ready for a small reviewed contribution when you can:

- [ ] Explain advisor WebAssembly versus the generated server-interactive Blazor sample.
- [ ] Build a component with a typed parameter and callback and explain parent ownership, lifecycle, and rendering.
- [ ] Trace draft selection through answer application, reevaluation, guide generation, and export.
- [ ] Explain Unknown/derived facts, the four evaluation outcomes, and why only Ready permits a plan.
- [ ] Demonstrate why changed answers invalidate dependent completion and no-op changes preserve it.
- [ ] Locate the evaluator behavior separately from rule metadata and add a meaningful boundary test.
- [ ] Generate/build the Web/API A/API B sample and locate JWT validation, scope enforcement, and OBO.
- [ ] Choose checks appropriate to UI, engine, guide/export, or generated-code changes.
- [ ] State what your checks prove and what still needs a real tenant or browser accessibility review.

If callbacks/lifecycle remain unclear, repeat the component drill with a teammate. If identity decisions remain unclear, start with UI/help work and pair on the engine/API task. Leave the session with one bounded issue, acceptance criteria, and a reviewer so that the first contribution can start this week.
